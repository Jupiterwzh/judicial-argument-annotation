# 文档规范

本文件是项目文档的总规范，约束仓库内所有文档。

## 1. 通用约束

1. **一处完整，其余链接。** 每个事实只在职责表指定的文档里完整写出一次；其他位置最多给一句结论加一个链接，不复制段落。同一规则写两遍，两处措辞迟早分叉，读者会拿到互相矛盾的指令。
2. **只写当前状态。** 不写“新增”“已实现”“即将支持”“原来是”“本次调整”，也不写评审与讨论过程；变更过程由 git 提交承担。需要长期保留的取舍理由，按第 3 节第 3 步先登记一种新的文档类型再落盘。spec 表头的版本与状态跟随当前内容更新。
3. **在 HEAD 可解析。** 引用一律指向仓库中真实存在的文件；不写“见上文”“第 4.7 节”“PR #12”“设计稿”这类离开当前会话就无法定位的指代，也不写提交号或日期标记；文档自身的版本与日期表头除外。
4. **读者决定写法。** 动笔前先明确读者是谁、在什么场景读、读之前已经知道什么。给新手的步骤型文档按“从零到完成”的顺序组织：先修概念先讲，只引入当前步骤需要的概念，难度逐级上升。查表型文档先划出检索范围，再按当前行为平铺，不设教学次序。两类内容同处一份时用标题分开，不把进阶材料塞进入门路径。
5. **位置决定范围。** 文档只写自己主题的内容，直接子文档只按目的与职责一句话带过，不罗列它的章节或要点，细节链接到拥有它的文档；主题范围不因文档类型而放宽。
6. **写契约，不写推导。** 每条规则保留执行者、触发条件与时序、模态（必须／可以／禁止）、失败与副作用、后果。结论的形成过程、被否决的局部写法、明显分支的证明一律删除。
7. **术语以 spec 的定义为准。** 统一使用命题（Premise）、结论（Claim）、论证关系、标签体系、标注任务、标注者、裁定者；不引入“论据”“前提”“标签集”这类近义替换。
8. **不动别人家和生成物。** 第三方来源、冻结的历史归档、生成产物只读；改动其源文件后重新生成，不手改产物。
9. **审查与修改分离。** 审查、审计类任务只报告问题，不顺手编辑；写文件需要明确授权，范围缺失时先问，不默认整个仓库。
10. **表格只回答一个问题。** 需要第二份清单时指向唯一出处；能由源码、配置或生成器产出的清单不手抄。
11. **长度以信息为界。** 已有上限优先遵守，不自行新增数字；删去任一行都会丢失契约或可核查事实，就是下限。过长指一次检索要扫过太多无关内容、或单个章节大到难以定位，不是字数。反复超长又没有上限时，报告缺预算并按职责表拆分，不为达标而删规则。
12. **语句具体。** 中文行文，一句话只承担一条规则。

## 2. 文档职责表

| 文档 | 唯一职责 | 读者 | 不写什么 |
|---|---|---|---|
| `docs/spec/<主题>.md` | 凡是对系统行为的约束都放这里：谁在什么条件下做什么、系统必须／可以／禁止什么、输入输出的判定标准、不可逆的流程顺序 | 实现者、评审者、测试作者 | 技术方案、库选型、代码结构、排期、界面视觉 |
| 根 `AGENTS.md` | 只放适用于任何目录、每次会话都必须生效的硬约束（技术栈、命令入口、协作边界）；一条一至三行 | 进入仓库的全部协作者与 AI | 单目录细则、教程、长清单 |
| 子目录 `AGENTS.md` | 只放本目录及其子目录特有、父级未覆盖的硬约束：本目录的命令、命名与分层规则、禁止触碰的边界、对父级规则的明确例外 | 只在该目录工作的协作者与 AI | 父级已有的规则、模块 API 说明、需求 |
| 根 `README.md` | 放新读者从零跑起来所需的内容：一句话说明系统做什么、安装与启动命令、最小可用流程、目录地图 | 新加入的开发者、外部读者 | 需求细则、模块内部结构 |
| 子目录 `README.md` | 放使用或集成该模块所需的内容：入口与命令、配置项及默认值、输入输出格式、失败与错误语义、限制与扩展点 | 使用或集成该模块的人 | 其他模块的职责、实现过程叙述、上级架构 |

同一事实在两类文档中冲突时，行为对错以 `docs/spec/` 为准；spec 未规定处以实现契约为准，不据 `AGENTS.md` 推断需求。`AGENTS.md` 的约束高于 README 的描述性说明；越靠近文件的 `AGENTS.md` 覆盖上级。冲突是缺陷：改到职责表指定的那一处，另一处只留链接。

## 3. 新内容的落位流程

1. **先定生效范围，再定内容类型。** 一条规则落多深，取决于它覆盖多少场景：对全部文档都成立，才进第 1 节；每次会话都要遵守，才进根 `AGENTS.md`；只在某类文档或某个目录成立，就进该类文档或该目录的 `AGENTS.md`。内容类型只决定去向，不决定深浅：行为与需求 → spec；上手与运行 → 根 `README.md`；模块契约 → 该目录 `README.md`。
2. **找家。** 这类内容已写在别处，就改那一处，新位置只留链接（见约束 1）。
3. **补表。** 表中没有这类内容时，先在第 2 节增加一行（职责、读者、不写什么），再创建文件或目录；不创建没有职责的文档。
4. **自检。** 新事实只有一个完整出处；每个引用都能在仓库里打开（见约束 3）；删掉解释变更动机的句子后，契约仍然完整（见约束 2、6）。

## 4. 修改职责表的原则

1. **表是准入规则，不是文档清单。** 一行定义一个“什么内容该放这里”的判断依据，不描述某份文档现在写了什么、分了几节、是否已创建。文件是否存在、内容多长，由仓库本身回答。
2. **职责列写准入条件，不写内容摘要。** 用“凡……的内容放这里”的形式，让人拿一段新内容就能判断放不放得进去。概括现有正文，表会随正文漂移，还会制造第二份同义内容。
3. **新增一行前先查重叠。** 现有某行已能收下这段内容，就改那一行；两行能用同一句准入标准收同一类内容，就合并或改写其中一行，不留边界模糊的条目。
4. **读者列必须具体。** 写具体的人群与阅读场景，不写“所有人”“相关人员”；读者如何影响写法见约束 4。写不出读者时说明职责边界未定，先定读者再定职责。
5. **删除或合并前先搬家。** 确认该行承载的契约已被别的行接收，再删；不把仍在生效的要求连同重复一起删掉。
6. **不复述表本身。** 一句话若只指出“某行属于哪一类”、或只列举受约束的文件名，它已被该行覆盖，删掉。表与第 1 节各说一件事，同一条规则不得两处各写一套。
